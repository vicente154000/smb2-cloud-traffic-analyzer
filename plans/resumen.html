2. Primer analizador (v1) src/analizador_smb2.py

2.1 ¿Cómo funciona?

El primer analizador que desarrollamos usa una estrategia de ventana temporal para agrupar paquetes. La idea es sencilla: si dos paquetes del mismo FileID (o del mismo TreeID si no tienen FileID) llegan con menos de 2 segundos de diferencia, asumimos que pertenecen a la misma operación. Si el silencio entre ellos supera los 2 segundos, los separamos en operaciones distintas.

Internamente, la función agrupar_por_operacion() (línea 284) hace lo siguiente: primero separa los paquetes por su identificador (FileID si tiene, TreeID si no). Luego, para cada grupo, los ordena por timestamp y los recorre secuencialmente. Cuando encuentra un salto temporal mayor de 2 segundos entre dos paquetes consecutivos, cierra la operación actual y empieza una nueva. Al final, ordena todas las operaciones por su timestamp de inicio para presentarlas en orden cronológico.

1. Separar paquetes por clave: FileID o TreeID
2. Para cada grupo, ordenar por timestamp
3. Si el salto entre dos paquetes > 2s → separar en distinta operación
4. Ordenar todas las operaciones por timestamp de inicio

2.2 ¿Qué problemas tenía?

⚠️ La asincronía del protocolo SMB2 rompe la ventana temporal:

El protocolo SMB2 permite que el cliente envíe múltiples solicitudes sin esperar respuesta. Esto significa que los paquetes de distintas operaciones aparecen entremezclados en la captura. La ventana temporal no puede distinguir si dos paquetes que llegan con 0.5s de diferencia pertenecen a la misma operación o a operaciones diferentes.

Ejemplo: El usuario abre un archivo (CREATE FID_A) y 0.5s después el sistema sincroniza con la nube (CREATE FID_B). Ambos paquetes caen dentro de la misma ventana de 2s y se agrupan juntos, aunque sean operaciones completamente distintas. Esto genera falsos positivos (operaciones mezcladas) y también falsos negativos (operaciones que deberían estar juntas se parten si hay un silencio >2s).
⚠️ Las reglas catch-all ocultaban los errores:

La v1 original incluía reglas "catch-all" al final de la cadena de clasificación. Estas reglas asignaban un tipo a cualquier operación que no hubiera coincidido con las reglas anteriores, lo que producía 0 operaciones DESCONOCIDA. Pero esto era engañoso: operaciones que no correspondían a ningún patrón real se clasificaban igualmente con el tipo más cercano, generando falsos positivos.

Ejemplo: Una secuencia anómala como CREATE + IOCTL + CLOSE se clasificaba como SUBIR ARCHIVO porque la regla catch-all detectaba WRITE, aunque realmente no hubiera ninguna escritura. Esto daba una falsa sensación de precisión pero ocultaba patrones reales que deberían investigarse. Al eliminar estas reglas, aparecieron operaciones DESCONOCIDA que revelaban limitaciones del agrupamiento.

2.3 ¿Qué resultados daba?

Tras eliminar las reglas catch-all, la v1 producía aproximadamente 5.000 operaciones en la traza de usuario. De estas, unas 54 aparecían como "complejas" porque la ventana temporal había mezclado operaciones de distintos FileIDs en una misma operación. El resto eran operaciones atómicas, pero muchas estaban mal delimitadas por el problema de la asincronía. Estaba claro que necesitábamos un enfoque más robusto.

3. Segundo analizador (v2) src/analizador_smb2_v2.py — EL ACTUAL

3.1 ¿Cómo agrupa los paquetes?

La v2 surge de una observación clave sobre el protocolo SMB2: cada operación comienza con un CREATE y termina con un CLOSE. El CREATE abre un recurso (archivo o carpeta) y asigna un FileID único. Todos los comandos posteriores (READ, WRITE, SET_INFO, etc.) usan ese mismo FileID para referirse al recurso. El CLOSE libera el FileID y marca el final de la operación.

Aprovechando esta estructura, la función agrupar_por_operacion() (línea 288) implementa una estrategia radicalmente diferente a v1: en lugar de usar ventanas temporales, separa los paquetes por FileID y busca secuencias CREATE → CLOSE dentro de cada grupo. Esto elimina el problema de asincronía de v1 porque cada FileID se procesa de forma independiente: si dos operaciones usan FileIDs distintos, nunca se mezclan, aunque sus paquetes lleguen entremezclados en la captura.

1. Separar paquetes: con FileID → por FileID; sin FileID → por TreeID
2. Para cada FileID, ordenar por timestamp
3. Buscar CREATE → añadir paquetes hasta encontrar CLOSE
├─ Si aparece otro CREATE antes del CLOSE → el anterior se queda sin cerrar (DESCONOCIDA)
└─ Los paquetes entre CLOSE y siguiente CREATE se descartan
4. Paquetes sin FileID (QUERY_DIRECTORY, QUERY_INFO) → TreeID + ventana temporal (como v1)

Los comandos QUERY_DIRECTORY (FIND) y QUERY_INFO no tienen FileID asociado, por lo que para ellos v2 usa el mismo enfoque que v1: agrupar por TreeID con ventana temporal de 2s. Esto es una limitación menor porque estos comandos suelen aparecer como operaciones independientes (LISTAR DIRECTORIO, CONSULTAR METADATOS) y rara vez se entremezclan con otras operaciones.

3.2 El problema de las operaciones multi-FileID

🔴 Punto crítico — Las operaciones "grandes" se rompen en operaciones atómicas:

Al agrupar por FileID, cada operación atómica tiene exactamente un único FileID. Esto es correcto para operaciones simples como SUBIR ARCHIVO (1 FileID), pero las operaciones "grandes" como COMPRIMIR ARCHIVO usan varios FileIDs y se rompen en operaciones atómicas separadas.

Ejemplo — COMPRIMIR ARCHIVO: Cuando el usuario comprime un archivo, el sistema operativo abre el archivo original (FID_ORIGEN) para leerlo y crea un archivo comprimido (FID_DEST) para escribir. Son dos FileIDs distintos, por lo que v2 produce dos operaciones atómicas:
  • FID_ORIGEN: CREATE + READ + CLOSE → se clasifica como BAJAR ARCHIVO
  • FID_DEST: CREATE + SET_INFO + WRITE + CLOSE → se clasifica como SUBIR ARCHIVO
Esto es intencionado: permite identificar con precisión qué comandos se ejecutaron sobre cada recurso. La consecuencia es que la operación "COMPRIMIR ARCHIVO" no aparece como tal en los resultados, sino como dos operaciones atómicas independientes. No existe un "ID de operación compuesta" en el protocolo SMB2 que permita agrupar varios FileIDs bajo una misma acción de usuario.

3.3 ¿Cómo clasifica las operaciones?

Una vez agrupadas, cada operación atómica se pasa por una cadena de 21 reglas en cascada (función clasificar_operacion(), línea 457). Las reglas están ordenadas de más específica a más genérica. La primera regla que coincide con la secuencia de comandos de la operación determina su tipo.

Cada regla verifica condiciones sobre la secuencia de comandos (CREATE, READ, WRITE, SET_INFO, CLOSE, etc.), los CreateOptions (si el recurso es un archivo o un directorio), los InfoClass de SET_INFO (0x0A para renombrar, 0x0D para borrar, 0x13 para AllocationInfo, 0x14 para FileEndOfFileInfo), y la presencia de operaciones de lectura/escritura.

🔴 Punto crítico — Solapamiento entre reglas:

Al ser en cascada, algunas reglas "tapan" a otras. Una operación puede cumplir las condiciones de varias reglas, pero solo la primera en el orden de evaluación se ejecuta. Esto genera algunos falsos positivos:
ProblemaExplicación
Regla 1 (LISTAR DIRECTORIO) captura SUBIR/BAJAR CARPETA vacía CREATE+FIND+CLOSE sin E/S → Regla 1 coincide antes que las reglas de subir/bajar carpeta (Reglas 9 y 10)
Regla 6 (SUBIR ARCHIVO) captura COPIAR ARCHIVO Regla 6 no verifica SET_INFO. COPIAR ARCHIVO (subida) tiene CREATE+WRITE+CLOSE, igual que SUBIR ARCHIVO. La diferencia real está en el SET_INFO con InfoClass=0x13, pero Regla 6 no lo comprueba
Regla 12 (COPIAR CARPETA) captura COMPRIMIR CARPETA Regla 12 se evalúa antes que Regla 14. COMPRIMIR CARPETA (FIND+CREATE+WRITE+CLOSE) coincide con los requisitos de COPIAR CARPETA porque ambos tienen FIND + escrituras
Regla 16 (MODIFICAR ATÓMICO) comparte patrón con COPIAR ARCHIVO CREATE+SET_INFO+WRITE+CLOSE. Se distinguen por el InfoClass: 0x14 (FileEndOfFileInfo) para MODIFICAR vs 0x13 (AllocationInfo) para COPIAR

3.4 Reporte de resultados

La función generar_reporte() (línea 690) produce un resumen estadístico con el recuento de cada tipo de operación, su porcentaje sobre el total, y las operaciones que no se han podido clasificar (DESCONOCIDA). También puede mostrar información de depuración para analizar casos concretos.

4. Tercer analizador (v3 — experimental) src/analizador_smb2_v3.py

4.1 Motivación

El v2 agrupa por FileID, lo que rompe las operaciones multi-FileID en operaciones atómicas. Se planteó: ¿y si agrupamos sin separar por FileID? Es decir, recorrer todos los paquetes cronológicamente y considerar que una operación empieza con un CREATE y termina cuando todos los FileIDs abiertos se han cerrado.

4.2 Estrategia: agrupar_por_ventana_global()

La función agrupar_por_ventana_global() (en src/analizador_smb2_v3.py, línea 242) implementa una estrategia completamente diferente a v2. Mientras que v2 separa los paquetes por FileID y procesa cada secuencia CREATE→CLOSE de forma independiente, v3 recorre todos los paquetes en orden cronológico sin separarlos por FileID.

Algoritmo paso a paso:

1. Inicializar: operación_actual = None, fids_abiertos = { }

2. Para cada paquete en orden cronológico:
├─ Si es CREATE con FileID:
│ ├─ Si no hay operación activa → crear una nueva
│ ├─ Añadir paquete a la operación actual
│ └─ Registrar FileID como "abierto" (pendiente de CLOSE)
├─ Si es CLOSE con FileID:
│ ├─ Añadir paquete a la operación actual
│ ├─ Reducir contador de CLOSE pendiente para ese FileID
│ └─ Si no quedan FileIDs abiertos → cerrar operación
└─ Si es otro comando (READ, WRITE, SET_INFO, etc.):
└─ Si hay operación activa → añadirlo. Si no → descartarlo (huérfano)

3. Si al final quedan FileIDs sin cerrar → DESCONOCIDA (CREATE sin CLOSE)

Diferencia clave con v2: En v2, cada FileID se procesa por separado. Si llega un CREATE de FID_B mientras se está procesando FID_A, v2 simplemente lo ignora porque está en otro grupo. En v3, ese CREATE de FID_B se añade a la misma operación que FID_A, porque el algoritmo no distingue entre FileIDs. La operación solo termina cuando todos los FileIDs abiertos se han cerrado.

Esto permite que operaciones como COMPRIMIR ARCHIVO (2 FileIDs: origen para leer, destino para escribir) o COPIAR CARPETA (decenas de FileIDs) se mantengan juntas en una sola operación, ya que sus FileIDs se abren y cierran en el mismo intervalo temporal.

4.3 ¿Por qué se planteó?

El planteamiento de v3 surge de una observación durante la validación. En el script tests/validar_todas_operaciones.py, las operaciones multi-FileID se clasifican correctamente porque se construyen manualmente con todos los comandos juntos (múltiples FileIDs en una sola operación) y se pasan directamente a clasificar_operacion(). El clasificador ve todos los comandos simultáneamente y puede identificar patrones como COMPRIMIR ARCHIVO (CREATE+READ+CREATE+SET_INFO+WRITE+CLOSE+CLOSE).

Esto llevó a preguntarse: ¿por qué no podemos hacer lo mismo en el analizador real? Es decir, en lugar de separar por FileID (v2), agrupar todos los paquetes que pertenecen a la misma "acción de usuario" en una sola operación y luego clasificarla.

El problema es que en el validador sabemos de antemano qué paquetes pertenecen a cada operación porque los hemos definido manualmente. En una traza real, los paquetes de distintos FileIDs llegan entremezclados en la captura y no hay ninguna señal en el protocolo SMB2 que indique "estos 2 FileIDs pertenecen a la misma acción de usuario".

La v3 intenta resolver esto con una heurística: "todos los FileIDs que estén abiertos simultáneamente pertenecen a la misma operación". Si el usuario comprime un archivo, los FileIDs del origen y del destino se abren y cierran en el mismo intervalo de tiempo, por lo que deberían agruparse juntos. Esta heurística parecía razonable y era el siguiente paso lógico después de comprobar que el validador sí podía clasificar operaciones multi-FileID.

4.4 Resultados

Traza_user_5.csv: solo 3 operaciones
  • 2 CREAR CARPETA (operaciones simples con 1 FileID)
  • 1 COPIAR CARPETA con 5.322 FileIDs — una sola operación gigante que abarca casi toda la traza
Traza_ransom_formato_tabla.csv: solo 1 operación
  • 1 OPERACIÓN COMPLEJA con los 26.742 paquetes de toda la traza

4.5 ¿Por qué no funciona?

El problema fundamental es el solapamiento de FileIDs en trazas reales. En una captura real, los FileIDs de distintas operaciones se solapan en el tiempo. Nunca se cierran todos a la vez porque:

  • Operaciones concurrentes: el usuario puede tener varias operaciones abiertas simultáneamente (ej: editor de texto con varios archivos abiertos)
  • Asincronía SMB2: el protocolo permite múltiples operaciones en curso sin esperar a que terminen
  • Dropbox/OneDrive: los clientes de sincronización mantienen conexiones persistentes con FileIDs abiertos durante minutos

Ejemplo concreto — solapamiento en la traza real:

t=1.0 CREATE FID_A (operación 1: abrir documento)
t=1.1 CREATE FID_B (operación 2: otra tarea)
t=1.2 READ FID_A
t=1.3 CLOSE FID_B ← se cierra FID_B, pero FID_A sigue abierto
t=1.4 CREATE FID_C (operación 3)
t=1.5 READ FID_A
t=1.6 CLOSE FID_C
t=1.7 CLOSE FID_A ← aquí se cerraría la operación, pero ya se han mezclado FID_B y FID_C

Como los FileIDs se solapan, la ventana global termina agrupando casi toda la traza en una sola operación. En el caso del ransomware, los 26.742 paquetes acaban en una única operación porque siempre hay al menos un FileID abierto.

4.6 Lección aprendida

La v3 demostró que no se puede agrupar sin separar por FileID en trazas reales. El FileID es la única señal fiable en SMB2 para delimitar operaciones atómicas. Cualquier intento de agrupar multi-FileID debe hacerse después de la clasificación atómica, no antes.

Este experimento llevó directamente al enfoque 5 (clasificador de segundo nivel, sección 9): primero clasificar por FileID (v2), luego fusionar operaciones atómicas relacionadas.

5.3 ¿Por qué no podemos saltarnos agrupar_por_operacion() en el analizador real?

En el validador podemos construir operaciones con múltiples FileIDs porque ya sabemos de antemano qué paquetes pertenecen a cada operación. En una traza real, los paquetes de distintos FileIDs llegan entremezclados en la captura y no hay ninguna señal en el protocolo SMB2 que indique "estos 2 FileIDs pertenecen a la misma acción de usuario".

Ejemplo real — COMPRIMIR ARCHIVO en la captura:

Timestamp FileID Comando
1.0 FID_ORIGEN CREATE (origen: documento.docx)
1.1 FID_ORIGEN READ
1.2 FID_DEST CREATE (destino: documento.zip) ← otro FileID se intercala
1.3 FID_ORIGEN READ ← vuelve al anterior
1.4 FID_DEST SET_INFO
1.5 FID_DEST WRITE
1.6 FID_DEST CLOSE
1.7 FID_ORIGEN CLOSE

Si no agrupamos por FileID, no hay manera de saber qué paquetes pertenecen a la misma operación:

  • Ventana temporal: No funciona porque los paquetes se solapan (FID_ORIGEN y FID_DEST se intercalan en el tiempo)
  • TreeID: No sirve porque es el mismo para todas las operaciones
  • Ruta del archivo: Podría ayudar (documento.docx → documento.zip), pero no es fiable al 100%

El FileID es la única señal fiable en el protocolo SMB2 para saber qué paquetes van juntos. Pero precisamente por eso, cada FileID genera una operación independiente. No existe un "ID de operación compuesta" en SMB2.

5.4 Posibles soluciones (trabajo futuro)

Para reconstruir las operaciones "grandes" a partir de las atómicas, se podrían explorar estos enfoques:

EnfoqueDescripciónLimitación
1. Fusión por relación de rutas Si dos operaciones atómicas ocurren en el mismo intervalo temporal y una lee de X.docx y otra escribe en X.zip, podrían fusionarse como COMPRIMIR ARCHIVO Requiere analizar nombres de archivo y extensiones. No cubre todos los casos (ej: COPIAR CARPETA no cambia extensión)
2. Ventana temporal + TreeID Agrupar operaciones atómicas del mismo TreeID que ocurren en una ventana de tiempo corta (ej: <5s) y tienen relaciones de E/S (una lee, otra escribe) Puede fusionar operaciones no relacionadas que coincidan en el tiempo. El umbral temporal es heurístico
3. Segundo nivel de clasificación Primero se clasifican las operaciones atómicas. Luego, un segundo paso busca patrones de operaciones compuestas analizando las relaciones entre ellas (misma ruta base, misma sesión, secuencia temporal) Más complejo de implementar. Requiere definir patrones de composición para cada operación "grande"
4. Machine Learning Entrenar un modelo que, dada una secuencia de operaciones atómicas, prediga si forman parte de una operación compuesta y de cuál Requiere un conjunto de datos etiquetado suficientemente grande

Ninguna de estas soluciones es perfecta porque todas se basan en heurísticas: no hay una señal en el protocolo SMB2 que garantice al 100% qué operaciones atómicas pertenecen a la misma acción de usuario.

9. Clasificador de segundo nivel (enfoque 5)

Como solución al problema de las operaciones multi-FileID, se ha implementado un clasificador de segundo nivel (src/clasificador_segundo_nivel.py) que toma las operaciones atómicas producidas por v2 y las fusiona en operaciones complejas cuando detecta patrones conocidos.

9.1 Estrategia

  1. v2 produce operaciones atómicas (1 FileID cada una)
  2. Segundo nivel recorre las operaciones ordenadas por timestamp y busca patrones de operaciones consecutivas que, juntas, forman una operación de nivel superior
  3. Cuando encuentra un patrón, fusiona las operaciones atómicas en una sola operación compleja con múltiples FileIDs

9.4 Limitaciones

  • Dependencia de heuristicas temporales: el umbral de 2s puede no ser adecuado para todos los escenarios
  • No detecta operaciones si hay ruido entre medias: si entre un BAJAR y un SUBIR hay un paquete de otra operación, el patrón se rompe
  • Solo funciona con operaciones consecutivas: no puede reconstruir operaciones si los paquetes están entremezclados con otras operaciones
  • No mejora la detección en ransomware: el ransomware no genera patrones BAJAR+SUBIR, por lo que el segundo nivel no aporta valor en ese caso
