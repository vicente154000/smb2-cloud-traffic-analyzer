1. Introduccion

Este documento recoge el proceso de desarrollo del analizador SMB2 v4, desde los problemas detectados en versiones anteriores hasta la implementacion final del nuevo algoritmo de agrupacion jerarquica. El objetivo es documentar tanto las decisiones de diseno como los problemas tecnicos encontrados, para que sirva como referencia en la redaccion de la memoria del TFG.

El codigo fuente del analizador v4 se encuentra en src/analizador_smb2_v4.py.

2. Problemas de las versiones anteriores

2.1 v1: Agrupamiento por ventana temporal

El primer analizador (src/analizador_smb2.py) agrupaba los paquetes usando una ventana temporal de 2 segundos: si dos paquetes consecutivos del mismo FileID/TreeID tenian una diferencia menor a 2 segundos, se consideraban parte de la misma operacion.

Problemas detectados:

  1. Falsa separacion por asincronia: En SMB2, el cliente puede enviar multiples solicitudes sin esperar respuesta. Esto provoca que paquetes de la misma operacion lleguen separados por mas de 2 segundos, fragmentando una operacion real en varias operaciones falsas.
  2. Falsa fusion por solapamiento: Si dos operaciones distintas ocurren en menos de 2 segundos (algo muy frecuente en la sincronizacion con la nube), sus paquetes se fusionan en una sola operacion, mezclando comandos de diferentes acciones.
  3. Resultado: 5.364 operaciones detectadas en la traza de usuario, muchas de ellas incorrectamente agrupadas.

2.2 v2: Agrupamiento por FileID (CREATE+CLOSE)

El segundo analizador (src/analizador_smb2_v2.py) cambio la estrategia: en lugar de ventana temporal, agrupa por FileID usando el par CREATE+CLOSE como delimitador.

Problemas detectados:

  1. Operaciones multi-FileID no detectadas: Muchas operaciones de usuario generan multiples FileIDs (uno por cada archivo involucrado). Al separar por FileID, estas operaciones se fragmentan en operaciones atomicas independientes.
  2. Reglas 8-15 inalcanzables: Las reglas que requieren num_creates >= 2 nunca se activan porque cada FileID se procesa por separado.
  3. FINDs sin FileID: Los comandos QUERY_DIRECTORY (FIND) no tienen FileID, por lo que se procesan aparte con ventana temporal.
  4. Resultados: Traza de usuario: 4.793 ops atomicas. Traza ransomware: 5.350 ops atomicas. Ninguna operacion compuesta detectada.

2.3 v3: Agrupamiento por ventana global

El tercer analizador (src/analizador_smb2_v3.py) fue un experimento para probar un enfoque radicalmente distinto: agrupar por ventana global sin separar por FileID.

Problemas detectados:

  1. Solapamiento masivo de FileIDs: Los FileIDs de diferentes operaciones se solapan constantemente debido a la asincronia del protocolo.
  2. Resultados inutilizables: Traza de usuario: solo 3 operaciones. Traza de ransomware: 1 unica operacion.

2.4 Clasificador de segundo nivel

Antes de desarrollar la v4, se intento un enfoque intermedio: el clasificador de segundo nivel (src/clasificador_segundo_nivel.py). La idea era tomar las operaciones atomicas de v2 y fusionarlas en operaciones compuestas mediante un post-procesado.

Problemas detectados: Fusion limitada (solo 16 ops en traza de usuario), sin efecto en ransomware, complejidad anadida.

3. El nuevo analizador v4

3.1 Acuerdo con el profesor

Tras analizar las limitaciones de las versiones anteriores, se llego al siguiente acuerdo con el profesor sobre la arquitectura del nuevo analizador:

  1. Agrupar CREATE-CLOSE con un algoritmo jerarquico: el primer CREATE de la traza es la "raiz" de una operacion compuesta. Cualquier CREATE que aparezca dentro del intervalo [CREATE_raiz, CLOSE_raiz] es un "subordinado".
  2. Extraer operaciones atomicas hijas de cada operacion compuesta (1 por FileID).
  3. Clasificar operaciones atomicas reutilizando el clasificador de v2 (21 reglas en cascada).
  4. Clasificar operaciones compuestas con un nuevo clasificador que opera sobre los paquetes raw.
  5. Integrar FINDs dentro de la operacion activa.

3.2 Arquitectura del pipeline v4

El pipeline de la v4 consta de 4 pasos:

1. Leer CSV/TXT (leer_csv)
   - Detectar formato automaticamente
   - Extraer paquetes SMB2
   - Filtrar comandos de ruido

2. Agrupar por operacion (agrupar_por_operacion_v4)
   - Pre-escanear FileIDs con CLOSE
   - Recorrer paquetes en orden cronologico
   - Primer CREATE con CLOSE -> raiz de OperacionCompuesta
   - CREATEs dentro del intervalo -> subordinados
   - FINDs sin FileID -> integrados en operacion activa
   - CLOSE del raiz -> cierra la operacion compuesta

3. Clasificar (por cada OperacionCompuesta)
   3a. Extraer operaciones atomicas (1 por FileID)
   3b. Clasificar cada atomica con clasificador de v2
   3c. Si es multi-FileID -> clasificar como compuesta

4. Generar reporte (generar_reporte_v4)

3.3 Estructuras de datos

La v4 introduce una nueva clase OperacionCompuesta que envuelve los paquetes de una operacion, ya sea simple (1 FileID) o compuesta (multiples FileIDs):

class OperacionCompuesta:
    id: str                    # UUID unico
    fileid_raiz: str           # FileID del CREATE principal
    paquetes: List[PaqueteSMB2]
    operaciones_atomicas: List[Operacion]
    es_simple: bool            # True = 1 FileID
    tipo_atomica: str
    tipo_compuesta: str

3.4 Algoritmo de agrupacion jerarquica

El corazon de la v4 es la funcion agrupar_por_operacion_v4():

1. Pre-escanear todos los paquetes para identificar que FileIDs
   tienen al menos un CLOSE (fids_con_close).

2. Recorrer paquetes en orden cronologico:
   a. Si NO tiene FileID (FIND, QUERY_INFO):
      - Si hay operacion activa -> integrar
      - Si no -> guardar para agrupar al final
   b. Si es CREATE:
      - Si su FileID NO tiene CLOSE -> descartar
      - Si no hay operacion activa -> es el raiz
      - Si ya hay activa y es mismo FileID -> cerrar y empezar nueva
      - Si no -> es subordinado
   c. Si es CLOSE:
      - Si esta en fids_abiertos -> anyadir y eliminar
      - Si es el CLOSE del raiz -> cerrar operacion compuesta
   d. Otro comando:
      - Si su FileID esta en fids_abiertos -> anyadir
      - Si no -> descartar

3. Si queda operacion sin cerrar -> anyadirla igualmente
4. Procesar paquetes sin FileID restantes

Ejemplo visual:

[CREATE FID_A]  <- raiz, inicia op_compuesta_1
  [QUERY_DIRECTORY]  <- FIND, se integra
  [READ FID_A]
  [CREATE FID_B]  <- subordinado
  [WRITE FID_B]
  [CLOSE FID_B]
  [CREATE FID_C]  <- otro subordinado
  [WRITE FID_C]
  [CLOSE FID_C]
[CLOSE FID_A]    <- se cierra el raiz

Resultado: 1 OperacionCompuesta con 3 FileIDs

3.6 Clasificador de operaciones compuestas

La funcion clasificar_operacion_compuesta() opera directamente sobre los paquetes raw. Solo se aplica si la operacion tiene 2 o mas FileIDs. Las reglas multi-FileID son:

FuncionReglaDescripcion
_es_copiar_carpeta()12CREATE(carpeta) + FIND + READ + WRITE, >=2 FileIDs
_es_comprimir_archivo()13CREATE(archivo) + READ + CREATE + SET_INFO(0x13) + WRITE, 2 FileIDs
_es_comprimir_carpeta()14CREATE(carpeta) + FIND + READ + WRITE + SET_INFO(0x13), >=3 FileIDs
_es_modificar_archivo_editor()15CREATE + READ + WRITE + IOCTL, >=2 FileIDs
_es_subir_carpeta()8CREATE(carpeta) + FIND + WRITE (sin READ), >=2 FileIDs
_es_bajar_carpeta()9CREATE(carpeta) + FIND + READ (sin WRITE), >=2 FileIDs
_es_operacion_compleja()19CREATE + READ + WRITE + SET_INFO, >=3 creates

4. Problemas encontrados durante el desarrollo

4.1 Problema: CREATEs huerfanos sin CLOSE

Contexto: Al ejecutar la v4 por primera vez sobre la traza de usuario (26.817 paquetes), solo se detectaron 10 operaciones compuestas. El resto de los paquetes quedaban atrapados en una unica operacion gigante.

Causa raiz: El primer CREATE de la traza tenia un FileID que nunca se cerraba. Como el algoritmo considera que el primer CREATE es el "raiz", y ese raiz nunca se cerraba, la operacion compuesta capturaba todos los paquetes desde la linea 37 hasta la linea 26.839 (25.580 paquetes, 4.758 FileIDs).

4.2 Solucion: Pre-escaneo de FileIDs con CLOSE

Solucion: Se anadio una fase de pre-escaneo (_pre_escanear_fids_con_close()) que recorre todos los paquetes antes del agrupamiento para identificar que FileIDs tienen al menos un CLOSE.

def _pre_escanear_fids_con_close(paquetes):
    fids_con_close = set()
    for pkt in paquetes:
        if pkt.file_id and pkt.comando == "CLOSE":
            fids_con_close.add(pkt.file_id)
    return fids_con_close

Resultado: En la traza de usuario se detectaron 77 operaciones (61 simples + 16 compuestas), y en salidaSemana.txt se detectaron 15.458 operaciones (9.842 simples + 1.523 compuestas).

4.4 Problema: FINDs con GUID cero en formato TXT

Contexto: Al integrar los FINDs en las operaciones activas, se observo que ningun FIND se integraba en la traza de ransomware (salidaSemana.txt), a pesar de que habia 869.750 comandos QUERY_DIRECTORY.

Causa raiz: En el formato TXT, los comandos QUERY_DIRECTORY tenian un FileID con valor 00000000000000000000000000000000 (GUID de 128 bits todo ceros). La condicion para detectar si un FileID estaba presente era:

file_id = None
raw = partes[14] if len(partes) > 14 else ""
if raw and raw != "0":
    file_id = raw

El problema es que "00000000000000000000000000000000" es truthy y no es igual a "0", por lo que el lector asignaba este GUID cero como FileID del paquete, impidiendo su integracion.

4.5 Solucion: Deteccion de GUID cero en el lector TXT

Solucion: Se anadio una comprobacion adicional:

if raw and raw != "0" and raw != "00000000000000000000000000000000":
    file_id = raw

Resultado: 2.572.008 paquetes sin FileID integrados en operaciones activas (869.750 QUERY_DIRECTORY + 805.182 QUERY_INFO). El 100% de los QUERY_DIRECTORY dentro del rango de una operacion activa se integraron correctamente.

4.6 Problema: Multi-formato de entrada (CSV y TXT)

El proyecto trabaja con dos formatos de entrada diferentes: CSV de Wireshark (formato tabla exportado) y TXT de salidaSemana (formato espacio-separado con 20+ columnas). Cada formato tiene distinto separador, numero de columnas, codificacion y cabeceras.

4.7 Solucion: Deteccion automatica de formato

Se implemento una funcion _detectar_formato() que analiza las primeras lineas del archivo para determinar el formato, redirigiendo al lector adecuado.

Nota importante: La v4 no produce "menos" operaciones que v2, sino que las agrupa de forma diferente. En v2, cada FileID genera una operacion atomica independiente (4.793 en traza de usuario). En v4, los FileIDs se agrupan por jerarquia (raiz + subordinados), produciendo 77 operaciones compuestas en la misma traza. Cada operacion compuesta de v4 contiene multiples operaciones atomicas de v2 como sub-operaciones. Por tanto, no son directamente comparables en numero: v4 ofrece una vision mas abstracta (operaciones de alto nivel como "COPIAR CARPETA"), mientras que v2 ofrece una vision granular (operaciones atomicas como "SUBIR ARCHIVO", "BORRAR ARCHIVO").

Conclusion: La v4 introduce la capacidad de detectar operaciones compuestas multi-FileID que v2 no podia identificar. En la traza de ransomware grande (salidaSemana.txt), se detectan 1.523 operaciones compuestas, incluyendo patrones como COPIAR CARPETA (138), BAJAR CARPETA (56) y SUBIR CARPETA (8). La integracion de FINDs permite clasificar correctamente estas operaciones. Sin embargo, el clasificador de compuestas aun deja 850 operaciones como OPERACION COMPLEJA generico (56%), lo que indica que se necesitan mas reglas para cubrir todos los patrones.

6. Limitaciones y trabajo futuro

6.1 Limitaciones actuales

  1. Clasificador de compuestas limitado: Aunque se detectan 1.523 operaciones compuestas en la traza de ransomware grande, 850 de ellas (56%) quedan sin patron reconocido (OPERACION COMPLEJA generico).
  2. Dependencia del pre-escaneo: Requiere recorrer toda la traza dos veces (una para el pre-escaneo, otra para el agrupamiento). Para trazas de 17 millones de paquetes, esto duplica el tiempo de procesamiento.
  3. FINDs fuera de operacion: Los FINDs que aparecen fuera de cualquier operacion activa se siguen agrupando por TreeID con ventana temporal (igual que v2).
  4. Soporte de formatos: Aunque se anadio soporte para TXT, el formato ODS no se soporta directamente. Requiere conversion manual a CSV.

6.2 Trabajo futuro

  1. Ampliar reglas del clasificador de compuestas: Analizar las 850 operaciones compuestas sin patron para identificar nuevos patrones y anadir reglas.
  2. Optimizar el pre-escaneo: En lugar de recorrer toda la traza dos veces, usar una ventana deslizante en una sola pasada.
  3. Clasificador binario ransomware/usuario: Usar las operaciones detectadas como caracteristicas para distinguir entre trafico legitimo y malicioso.
  4. Soporte para ODS: Anadir un lector de archivos ODS para evitar la conversion manual.
  5. Visualizacion temporal: Generar graficos con la distribucion temporal de las operaciones para identificar patrones visualmente.
